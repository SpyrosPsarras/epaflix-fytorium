# Fytorium Android

Kotlin and Compose phone app, API 29 through 35. Login, Today and Upcoming use the real server. Today, Upcoming and previously loaded plant data stay readable offline. Plants supports native editing and lifecycle actions. Photo updates, the journal and photo identification use the same server endpoints as the web. Firebase Messaging delivers app notifications. No analytics or external crash service is included.

## Run from the repository root

All compilation and tests run in Docker. Only Docker, its Compose plugin and the existing shell scripts are needed on the host.

```sh
./scripts/android build
./scripts/android test
./scripts/android lint
./scripts/android screenshots
./scripts/android release-check
./scripts/container install --frozen-lockfile
./scripts/stack up
./scripts/android e2e
./scripts/android release-launch
./scripts/stack down
```

The SDK image uses JDK 17.0.14+7 with a digest-pinned base, command-line tools 12.0, platform 35 revision 2, build-tools 35.0.0, and platform-tools 37.0.1. The emulator target adds emulator 37.2.12 and Google APIs API 35 x86_64 revision 9. Archive checksums are checked during the build. Package metadata for the emulator is checked in because command-line tools 12 does not discover its archive from source.properties alone.

Gradle 8.11.1 uses a checked-in wrapper and distribution SHA-256. Every direct plugin and dependency version is in `gradle/libs.versions.toml`. Gradle caches live in `android/.gradle-cache/` and are gitignored. Docker writes no Android installation to the host. The emulator image is not needed by CI.

The debug APK is `android/app/build/outputs/apk/debug/app-debug.apk`. Test, lint and emulator reports are under `android/app/build/reports/`. A debug-only network security config permits cleartext HTTP only for the exact local hosts `app`, `oidc` and the instrumentation-only fake receiver `fake-push`, without subdomains. Its base policy and the release manifest forbid cleartext. Production defaults to `https://fytorium.epaflix.com`; the Gradle property `serverUrl` overrides this build setting. Release builds reject non-HTTPS URLs before compilation. `release-check` assembles an unsigned R8-minified, resource-shrunk APK and reports its size. Compose, AndroidX, coroutines and OkHttp supply their consumer keep rules; app models use direct Kotlin access and built-in JSON, with no reflective serializer to keep. `release-launch` requires the running stack and installs the release APK using an ephemeral container-only signing key, checks the login UI and process, and rejects crashes. The e2e script builds with `http://app:3000`. Ordinary build/test/lint commands reset it to production.

## Emulator networking and ownership

The emulator container joins this worktree's Compose network. Inside the container, dnsmasq forwards guest DNS to Docker's resolver at 127.0.0.11. The guest emulator is started with that container's IP as its DNS server. It can therefore reach both canonical origins, `http://app:3000` and `http://oidc:8080`, without published ports, changed OIDC callbacks or host DNS edits. Before instrumentation, bounded readiness gates query dnsmasq directly for both names, check stack HTTP from the container, then issue HTTP requests to both names with `adb shell` inside the guest. Each gate has a configurable deadline and reports the failed probe and DNS logs. dnsmasq does not cache early negative answers. The emulator runs with `-feature -WiFiPacketStream`, which disables Netsim Wi-Fi packet streaming because it can strand guest DNS under CPU load. The emulator's own DNS proxy at 10.0.2.3 sometimes stops forwarding queries anyway: the guest gets "No address associated with hostname" while dnsmasq sees no guest queries. So after boot, `docker/e2e` adds guest-only `iptables` NAT rules that redirect 10.0.2.3:53 (UDP and TCP) straight to the container's dnsmasq. These rules need guest root (`su 0`), which the pinned Google APIs userdebug image provides. They exist only inside the disposable test emulator and never touch the app or the release build. The exact trigger inside the emulator is unproven. If readiness still times out, the gate prints the guest resolver state and the dnsmasq log. An instrumented test still asserts both endpoints respond from the guest, not merely from its container. adb binds to container-local `127.0.0.1:5037`, with inherited adb endpoints cleared and the fresh `emulator-5554` selected. The container uses bridge networking, not the host network, and mounts no host adb socket.

`./scripts/android e2e` requires a running stack from `./scripts/stack up`. It boots a fresh AVD with `--device /dev/kvm`, installs the debug APK and runs instrumented tests. The container runs as the caller's UID with the KVM device group, so caches remain caller-owned. The AVD is ephemeral, so the second run has no old browser cookies or device credentials. The script checks that Chrome is installed, selects it as the guest debug app so it reads test command-line flags, and disables first-run onboarding and the default-browser prompt. These settings exist only in the disposable AVD; they do not bypass OIDC or change the app's network policy. Boot waits are bounded. The emulator container has a unique name and is removed on exit, including failure. INT and TERM exit through cleanup. The stack is never started, rebuilt or stopped by e2e; it stays running for the next run.

The disposable AVD sets `captive_portal_mode=0`, then reconnects Wi-Fi and mobile data so new network monitors read it. Android skips its connectivity probes and treats any connected network as `VALIDATED`. Airplane mode still exercises offline behavior, but connected networks without validation are not covered by this e2e and rely on unit tests. External Google captive-portal probes cannot reliably finish on the private Docker network. The stack's `/healthz` returns a non-empty HTTP 200 JSON body, not the empty 204 expected by those probes, so pointing portal URLs there would misclassify the stack as a portal. No production device settings change. The container and guest must still resolve `app` and `oidc` and receive real HTTP 200 responses before instrumentation; airplane-mode recovery still checks validated connectivity, DNS and app HTTP.

Readiness timeout overrides are whole seconds from 1 to 3600:

| Environment variable | Default | Readiness check |
| --- | --- | --- |
| `E2E_BOOT_TIMEOUT` | 360 | Guest reports `sys.boot_completed=1` |
| `E2E_PM_TIMEOUT` | 180 | Guest package manager responds to `pm path android` and the phone service, which `svc data` needs, is registered |
| `E2E_DNS_TIMEOUT` | 180 | Container dnsmasq resolves `app` and `oidc`, and stack HTTP responds |
| `E2E_GUEST_NETWORK_TIMEOUT` | 180 | Guest reaches both HTTP endpoints before instrumentation; also bounds validated-network, `app` DNS and HTTP recovery after airplane mode |

To run five times on exactly the same stack:

```
./scripts/container install --frozen-lockfile
./scripts/stack up
for run in 1 2 3 4 5; do
  E2E_LOGIN=1 ./scripts/android e2e || exit 1
done
./scripts/stack down
```

The stack keeps species and their fetched names between runs. A05 and A11 expect the stack's familiar name, Synthetic cloudleaf, when Fytorium already has the species, after waiting for its names to be fetched, and the canonical name Testoria nebulosa when it does not. Scenarios switch tabs as a user would: they swipe away a receipt that covers the navigation bar and tap the tab once the bar takes taps again. The disposable AVD also sets `hide_error_dialogs=1`, so an "isn't responding" dialog from a busy image app, such as the Google SDK setup app, cannot cover Chrome or Fytorium; the system ends that app instead, and a Fytorium crash or ANR still fails the run. A failing LaunchTest test (it runs every scenario) saves a screenshot and the uiautomator window dump to the guest's shared storage before its activity closes, and the script pulls them into `.scratch/e2e-failures/`.

The launch, guest networking and real Android Keystore round-trip tests always run. `E2E_LOGIN=1` also enables the Custom Tab scenario against the merged A01 login endpoints. It waits for the local provider in Chrome, enters and verifies subject `synthetic-a03-owner`, scrolls forward to Sign-in and waits for the redirect to return to Fytorium. It seeds a synthetic site and Testoria plant through the bearer API, advances the stack's `__test/clock`, completes a late watering task and undoes it, checks a future Upcoming row has no Snooze, then enables real guest airplane mode. Cached Today stays visible, writes are disabled and a disabled click produces no care event after reconnecting. After disabling airplane mode, a readiness gate bounded by `E2E_GUEST_NETWORK_TIMEOUT`, default 180 seconds, waits for the default network to be validated, `app` to resolve, and a fresh HTTP health request to succeed before the next scenario request. Only readiness probes retry, not repository refreshes or scenario API calls. Network loss evicts idle API sockets so requests cannot reuse connections aborted by airplane mode. API sockets also expire after one idle second, before the local server's five-second keep-alive timeout; transport retries remain disabled. The scenario deletes its plant/site, resets the clock, logs out, checks the local wipe and checks WorkManager cancellation. Interrupted-run recovery deletes only fixtures with this scenario's exact synthetic names. The phone viewport needs scrolling past the provider's claims textarea. Only forward swipes are used, since a scroll-to-beginning gesture can trigger Chrome's pull-to-refresh and erase the entered subject. No mocked token endpoint replaces the server. The Google APIs image supplies Chrome for Custom Tabs. The emulator stays on homePC, not GitHub CI.

## Today

Today has a centred title and a Today/Upcoming switch above the cards, without a greeting, daily tip or summary counts. Due dates and lateness remain server values. Empty sections are hidden. An empty day shows the next server Upcoming task, and an empty collection offers Add plant and owner-only Planta import. Sitters with no shares see a separate empty message.

Each server section is a rounded card headed by its care type, or by its plant or site when rows are sorted by plant or site. Under plant sort a card's rows show the task and site without repeating the plant name. Under site sort rows show the plant name without the site. Row order within each card stays server-owned. Upcoming heads each day Today, Tomorrow or a day such as Thursday 19 Nov and holds that day's cards in the same grouping. Rows outside a care-type card name their care type. Cover IDs come from TaskList and load only `/thumb` through the existing 50 MiB ThumbnailCache. Sitters retain their existing photo restrictions, so the server projects a null cover and the app shows an initial. A one-line pill overlaps the photo's bottom edge for pending late tasks: `7d late`, or `2mo late` from 60 days, using whole 30-day months. Snooze and circular completion controls stay on the row. A row keeps the same width for its snooze and done or Undo controls in every state (pending, done, snoozed, skipped, saving, offline) and in every Today and Upcoming card, so its name never re-wraps after an action, even when an Undo brings an overdue task back into a future day's row. Done, Snooze, Skip and both Handle all tasks buttons show a snackbar receipt with Undo for 10 seconds, such as "Watered Thyme", "Fertilized and watered Thyme", "Snoozed watering for Coleus until Thu 19 Nov", "Skipped cleaning leaves for Coleus until Tue 15 Dec", "Watered 9 plants" or "Handled 3 tasks for Thyme". Undo reverses exactly what the receipt names, then says what it reversed, such as "Undid watering for Thyme", "Undid fertilizing and watering for Thyme", "Undid snooze of watering for Coleus" or "Undid watering for 9 plants". The wording comes from the server. A completion with non-empty `linked_events` adds "and watered". A Handle all tasks card batch adds "and watered" when its `batch_event_count` is larger than its `batch_plant_count`. Batch receipts count those two server fields, never the rows on screen. Failures show the server's message without Undo. The server lists every completion you made today as its own row, at the due date of the occurrence it completed, so it keeps its filled check and its place after a refresh or restart. The app shows the rows the server sends; between a write and the next refresh it patches only the row it acted on. Tapping the filled check undoes a single completion, or shows the batch receipt again for a batched one. TalkBack names the task on every check: "Water done for Thyme, Kitchen. Double tap to undo", "Fertilize and water done for Thyme, Kitchen. Double tap to undo both" when liquid fertilizing also recorded water, or "… Part of a batch of 4 plants. Double tap to see the batch". After any Undo, including the feed's rain Undo, the app replaces Today and Upcoming with the `today` and `upcoming` lists in the undo response, which the server builds exactly as `GET /api/tasks` does. Every row the Undo reverses shows its earlier state at once (late badge, Snooze, pending circle), and a snoozed or skipped task returns to Today. A task you snoozed or skipped today keeps its row and place for the rest of the day, with no check or circle. Its site line ends with the snooze or skip glyph and "until Thu 19 Nov" from the row's `postponed_until`, which TalkBack reads as "Snoozed until Thursday 19 November". When the line is too narrow the site goes first, then the weekday ("until 19 Nov"). An undo-arrow button in the done circle's place reverses that snooze or skip. Every row keeps the line under its name, empty for a sitter's row without a site, so the label never changes the row's height. When that line is empty, the name is centred on the photo. The occurrence it postponed is listed at its new date in Upcoming, labelled Snoozed or Skipped from the task's `postponed` field; on a narrow line its site is dropped whole instead of being cut. A care write shows progress only on its own row or button; other rows stay usable and their taps wait their turn. The pull-to-refresh spinner appears only for a pull and stays until the feed has refreshed too. App resume, network changes and writes refresh without it. Tapping the photo or name opens the plant page, whose Care row for that task shows the occurrence tapped. Today and Upcoming keep separate scroll positions, and Back returns to the selected view at the same position. Owner and family see Handle all tasks at the bottom of each Today care-type card with pending due or late tasks. It completes that care type across plants, follows the saved location filter and has one Undo for the whole batch. Under plant sort the same button completes that plant's due and late tasks; site cards have none. Once a card has nothing pending, the button keeps its place, disabled, and reads All done, or Nothing due today when its remaining tasks were only snoozed or skipped. Under plant sort the button's text leaves out the plant name; TalkBack still reads it, such as "All Thyme tasks done". Upcoming and sitters do not show this button. The top bar holds Search, the selected view's title (Today or Upcoming), Task view and, for owner and family, Add plant. Task view opens a sheet with segmented Sort and Filter buttons and Show others' completed tasks. The sheet opens fully, with its status line above the navigation bar. Each choice saves at once and the sheet says Saved, or shows the error and keeps the previous choice. Offline the sheet says "Task view needs a connection." and its choices are disabled; while Fytorium isn't responding it says "Task view needs Fytorium to respond." and asks Fytorium again every 5 seconds. The message clears as soon as changes work again. Disabled segments keep the selection visible, and every disabled choice dims alike, including the Show others' completed tasks label. A view other than the default shows as chips under the Today/Upcoming toggle, such as Indoor or Sorted by plant, with one Reset. With a filter, an empty day says "No indoor tasks today" and offers Show all. A sitter with no shared plants is told to ask the household owner. Today has no floating button. The list keeps normal bottom padding and never changes size for a receipt. A receipt, or the explanation a disabled control gives on tap, takes the navigation bar's place for its duration, so it covers no row, mid-list or at the end; a swipe dismisses it early. It fades in and out over the bar's items, so the bar is never blank. Until it has fully faded in, a tap on a tab still switches tabs. For half a second after a receipt or explanation goes, the bar ignores taps, so a late tap meant for Undo does not switch tabs. Its text takes at most two lines and ends with "…" when longer, so it fits the bar also at 1.3x text, and TalkBack reads the whole wording. No care action, Undo or receipt moves a visible row. While you are on Today or Upcoming, a refresh changes rows only in place: the acted row, labels, counts and receipts. Cards and rows that a refresh adds or removes, such as a snoozed task's new date in Upcoming or another member's completion, and the feed strip appearing or going, wait for the next pull, Today/Upcoming switch, return to Today or app resume, and so do renamed plants, sites, custom tasks and card headings, and the empty state after the last plant or share goes. Then the list is what the server last sent. A new task view and a new household day apply at once, together with the Today/Upcoming switch or the empty state, so yesterday's rows never stand in for today's. Until then a row turns into another occurrence only through this device's own write or Undo, as its response names it. Each event a write created, from a single care action, its linked water, a plant or card batch or rain watering, takes over only the pending row with its plant, task and `due_on`. A pending row of the same task with another date was already gone on the server, for example after another member's skip, so it keeps its place without controls. An Undo's response names, for each event it reversed, the pending occurrence it brought back, or none; the app never picks a pending row by plant and task alone. A skip that kept the date the task already had brings back its unpostponed occurrence, and the server names that one too. When the response names none for this device's own snooze or skip, the row takes what this device's later writes made of the occurrence that snooze or skip had postponed, such as the water a liquid fertilizing recorded for it, and never a pending occurrence of that date that another member's snooze or skip left. A row one change away from an occurrence takes it before a row that reaches it through more changes. A row the server no longer lists keeps its place with its controls disabled, so it cannot be acted on twice, and no other occurrence takes its place. Tapping one of those controls says "This task changed elsewhere. Pull to refresh." and writes nothing. A row this device's own Undo reversed, when what the Undo brought back is not left for that row, keeps its place without controls and reads Undone where its date or label was. Search opens the existing offline plant search. Notification and feed settings stay in More. Today background loading never disables Add plant or import. Offline, or while Fytorium isn't responding, Add plant and Planta import look disabled and a tap says why, and a second line under the Today or Upcoming title says so: "Offline · updated 13:29" or "Fytorium isn't responding". The top bar is always tall enough for both lines, also at 1.3x text, so losing or regaining the connection never moves or covers a row. Tapping the line opens its explanation, which says what the state means and what still works without repeating the time, such as "This phone can't reach Fytorium. You can still see the tasks from the last update. Changes need a connection.", with the feed's connection line under it. The same line carries Today's other messages in their own words, such as a refused refresh, "Rain watering is not ready. Try again in a moment." or "Feed settings saved."; the explanation of a refused refresh offers Try again; a feed message does not, because Try again refreshes and would not send Mark watered again; nothing is added above or between the cards when one starts or ends. A disabled check, Undo or snooze control also says why on tap: "Changes need a connection.", "Changes need Fytorium to respond." or "Update Fytorium to make changes." TalkBack reads the same reason as the control's state, including "This task changed elsewhere. Pull to refresh." A cold start shows the cached list in its first frame, never "Loading tasks…".

Every API request sends the phone language in `Accept-Language`. A plant shows its nickname, else the common name the server picked in the phone language, else the English one, else the canonical name. Supported common-name languages are `en`, `nb` and `el`; `no` and `nn` map to `nb`, and other languages fall back to English. Today, Upcoming, Plants and the plant page use the same name. The plant page shows the species' canonical name under its photo and the scientific name with author under Details. Offline snapshots keep the last server name until a refresh.

`TodayPresentationTest`, `RepositoryTest` and `TodayNavigationTest` cover grouping, batch actions, cached reads and navigation. `TodayRedesignScreenTest` records nine light/dark variants under `app/src/test/screenshots/a15-*`: many synthetic covers with late badges, mixed groups, Upcoming, empty day, filtered empty day, no plants, offline, family and sitter. The real-login scenario seeds eight synthetic plants and generated covers through the API, captures Today, Upcoming and the empty day in both themes, then removes only its named fixtures and restores settings. Captures are published to MediaStore Pictures in the disposable guest before Gradle uninstalls the APK and removes its app files. Publishing generated images requires no storage permission on API 29 or later. `./scripts/android e2e` pulls those real device captures into `.scratch/a15-emulator/`. No owner photos or Planta artwork are used.

## Photos, journal and identification

The Journal tab and a plant's "Photos of <name>" page show photo-first cards in a grid of columns at least 320 dp wide (two on a phone in landscape), newest taken date first. Each card fills its width with the photo at 4:3, loaded from the server's 1080 px display copy into the existing 50 MiB thumbnail cache, with its space kept before it loads. Under it: on the Journal the plant name as a 48 dp link and the date, on a plant's page the date; then "Cover photo", "Health: …" and the note. One ⋮ button per card ("Actions for the 15 Nov 2026 photo of <name>"; two photos of one plant from one day read "<name>'s photo 2 of 2 from 15 Nov 2026" here, on the photo and in Delete) offers Use as cover (not on the cover) and Delete. Delete asks "Delete this photo?" with the photo and a line naming the date and plant, then gives the receipt "Deleted the 15 Nov 2026 photo of <name>"; a new cover gives "<name>'s cover photo changed". Neither offers Undo. The top bar holds the title, a + button and the shared status line; pull to refresh replaces the Refresh button. An empty list shows "No photos yet" and "Add your first photo". Each list's last answer is kept in the member's Room cache, so offline the cards stay with "Offline · updated hh:mm" in the line, and +, ⋮ and Add photo update look off and say "Photo changes need a connection." on tap. The grid keeps its place while the viewer, the add form or a plant page is open.

Tapping a photo opens a full-screen dark viewer, without the app tabs, with Back and "<name> · <date>". The display copy shows at once and the original replaces it at the same fitted size. Pinch zooms between 1x and 5x, double tap toggles 1x and 2.5x around the tapped point, and a zoomed photo pans no further than its edges. Offline the line says "Offline · showing a smaller copy". The original is fetched into memory and discarded when the viewer closes. A 426 from any photo request shows the app-wide Update Fytorium screen.

Journal + opens "Choose a plant", the Plants grid with its search and without + or Graveyard; a plant opens the add form for it. Back walks form, picker, Journal. A plant page's + and its Add photo tile open the form directly. The form, "Add a photo of <name>", starts with Take photo and Choose photo tiles; a chosen photo shows at 4:3 with Replace (Take photo, Choose photo) and Remove. Then Taken on, Photo health (Not set by default), Note and Add photo update, which without a photo looks off and says "Choose a photo first.". Upload progress runs along the top edge; success returns to the page the user started from with "Added a photo of <name>", and a failure keeps every value with the reason under the button.

Every photo input offers Take photo and Choose photo (Choose photos on Identify). Take photo uses `ACTION_IMAGE_CAPTURE` with a non-exported FileProvider limited to `cache/captures/`. These files are temporary camera outputs, not cached photos. Replacing or removing a selection, successful upload, confirmed discard, leaving the route and logout remove them and their draft markers. Application startup deletes orphaned captures off the main thread; new camera captures wait for that cleanup to finish. Rotation preserves a pending camera output. Startup cleanup retains captures younger than ten minutes and any capture marked as held by an unsaved draft, regardless of age. An old unreferenced capture is still removed; a marked capture whose draft Android dropped (reboot, force stop) stays until logout or cache eviction. These temporary files remain subject to Android cache eviction. Choose photos uses AndroidX's Android Photo Picker contracts, single selection for updates and up to five for identification. Selected gallery images keep a persistent read grant through process recreation when their provider offers one; removal, replacement, successful upload, confirmed discard, leaving the route and logout release only grants that were taken. Providers without a persistent grant still attach using their temporary read grant; if Android kills the app before such a draft is saved, the restored draft shows the photo but cannot upload it, so choose it again. The manifest requests the Play services Photo Picker backport for Android 10 through 12; devices without a picker use the contract's system document fallback. No storage or camera permission is requested.

`ImageDecoder` applies source orientation, scales the long edge to at most 2560 pixels and a fresh JPEG encoder at quality 85 strips EXIF, including GPS. Processing and uploads run off the main thread. The decoder reads directly from the content URI or capture file, using its target-size listener instead of buffering the original input. Unreadable images and memory exhaustion show a clear input error without blocking replacement or retry. Previews and cards decode in a background coroutine at the available width, over a placeholder of the same size. Encoded uploads still obey the server's 15 MiB per-image and 40 MiB identification limits. Multipart uploads use the process-owned authenticated client, retain refresh-on-401 behavior and report bytes sent. Sending all bytes is separate from the server accepting the upload. Failures retain the form and selected images for retry; nothing is queued.

Photo update drafts keep the note, health, selected image URI and date through saved-state recreation. The Taken on picker also keeps an unconfirmed date. Toolbar Back, system Back, the navigation bar and notification taps ask before discarding a changed update, naming the plant. Confirmed discard clears its fields and image selection. Photo deletion keeps its target while the gallery reloads; Identify keeps its chosen candidate and search receipt; an original photo reopens by ID without saving its image bytes. The shell saves its discard question and destination as data, so Keep editing and Discard still work after recreation.

Add plant and Change species both offer Identify from photos. Identification keeps one to five selected images, displays the server's ordered scores, GBIF confidence and remaining quota, and requires explicit confirmation before passing the server search receipt to the existing plant form. Health choices and today's date come from `/api/choices` and `/api/meta`. Photo and identification controls use validated device connectivity, session/member/role gates and their own saving and error state. Care refreshes and care-server failures do not disable them. Sitters never call photo, journal or identification endpoints.

The A06 emulator scenario runs inside the real-login test when `E2E_LOGIN=1`. `photos/PhotoScenario.kt` generates a solid-colour synthetic 3200×1200 PNG in the target app's temporary FileProvider directory. An instrumentation activity monitor returns its content URI as `RESULT_OK` to the actual Photo Picker contract. A second monitor intercepts `ACTION_IMAGE_CAPTURE`, checks its private output URI and writes a synthetic JPEG there before returning `RESULT_OK`. Neither hook exists in the production app. Upload, cover, journal, the fake Pl@ntNet request, mandatory confirmation and adding the identified species all go through the real app and API. Fixture recovery and cleanup match only A06's exact synthetic names.

Repository tests cover scaling, EXIF rotation/GPS removal, multipart fields and progress, invalid/unreadable images, server errors, sitter/offline guards, identification scores/quota and uncached originals. Cleanup tests cover startup and logout without deleting unrelated cache files. JVM and device tests generate a 144 MB, 48-megapixel BMP one scanline at a time, then check URI upload and display-size decoding. Robolectric's Linux native decoder cannot decode file descriptors, so JVM tests use a test-only memory-mapped source adapter; device tests exercise the real content-resolver source. Compose accessibility tests and 20 light/dark reference images cover the gallery, journal, original, form, date picker, deletion dialog, failure, upload, suggestions and confirmation.

## Planta import

More → Import from Planta is owner-only. The code step says to get a one-time app code from the Planta App Portal, links it ("Open Planta App Portal"), takes the code in a password field (Go on the keyboard fetches) and says what fetching again changes. Once a review exists it folds into "Fetch again with a new code". The review heads with a summary such as "4 plants: 1 ready, 2 need a choice, 1 skipped". Plants that need a choice come first as open cards: the Planta photo, the name the plant will have (the server's `display_name`), "From Planta: <scientific name> · <site>", then "Choose the species" with reference-photo tiles ("This is my plant"; "Looks most like your photo" or "Not sure: import as <Genus> (any kind)" from a photo suggestion), Search for another species and Skip plant. Ready, skipped and imported plants are one compact row each ("Ready", "Skipped" or "Imported"); tapping a row unfolds its details and actions (Change species or skip, Undo skip, Open imported plant). Details read as sentences: "Plastic pot · 17 cm · All-purpose soil", "Last watered 10 Nov", "Photo comes with the import", leaving out what Planta did not say. Last care timestamps show in the phone's time zone. An import bar stays at the bottom while the review is open: "Still to choose:" with the first two names, which scroll to their cards, or "1 skipped plant stays out.", above "Import 2 plants", which explains "Choose a species or skip the plants above first." while a choice is left. Importing shows the receipt "Imported 2 plants", then "Import complete" with View imported plants and, while an imported site still has default conditions, "Check sites", which opens Plants → Sites. Re-import updates Planta-sourced species, cultivar, site, pot and soil, including owner edits, while retaining local settings. A name you give a plant in Fytorium stays until its name in Planta changes. The review is not kept offline: offline the page shows the code step, Fetch says "Importing needs a connection." on tap, and the line under the title says Offline.

The code stays only in an unsaved password field until submission, which clears it before the request, including on failure. It never enters Room, preferences, saved state or diagnostics. Code-exchange errors never relay upstream response text. Staging, selections and commit eligibility come from `/api/import/planta`; opening or restoring the route fetches that review without another code. Import controls use validated connectivity, the owner/session gates and the import's own request state, not Today background refreshes.

`planta/PlantaScenario.kt` runs inside the single real-login test. It uses only the stack's fake Planta, restores the review across Activity recreation, confirms the fuzzy Testoria match, imports its cover and checks the plant in Plants. It deletes only the fake import's exact synthetic plant/site names before and after each run, so repeated runs on one stack start a fresh review. Repository/state tests, saved-state tests and 18 accessible light/dark snapshots cover the code, review, search, confirmation, offline/error states and cover results.

## Login and diagnostics

Login opens `/auth/login` with `app=android`, the fixed `com.epaflix.fytorium:/oauth2redirect` URI, S256 challenge and a fresh 256-bit state. The app checks the exact hostless URI, state, duplicate query parameters and a ten-minute local login-attempt expiry. A validated redirect consumes the attempt before exchanging a code. Invalid or stale redirects cannot consume a newer pending attempt. Redirects received after login are ignored with a predefined debug-only logcat event, not a user error. The server's one-time code expiry remains 60 seconds.

Both tokens and the pending verifier/state are AES-256-GCM encrypted with an Android Keystore key. Pending state survives process recreation. No backup or device transfer may carry credential files. All API requests use a bearer token when logged in. The Application owns the API client, credential store and SessionController. SessionController exposes loggedIn, busy, message and updateRequired as a StateFlow, deriving loggedIn only from the credential store token flow. Login completion, version checks, refresh and logout run in its process-scoped coroutine scope. Its redirect queue and in-flight exchanges survive Activity recreation; Activities only forward fresh intents and render session state. Code and refresh exchanges use a separate HTTP client with no idle pooled connections. The browser round-trip can outlive the startup API socket, and these single-use requests must not automatically replay after a broken connection. Ordinary API calls still use their connection pool. A process-wide lock serializes refreshes across clients, re-reads the store, and reuses tokens already rotated by another caller. A 401 triggers at most one refresh and one replay. Only an explicit `invalid_grant` or `invalid_token` refresh rejection clears credentials and returns to login. Rate limits, server failures, malformed responses and network errors retain tokens and show a retry message. A retry sends the same stored refresh token after a lost reply, matching login contract Amendment 1. Restored Activities skip the old redirect intent; fresh redirects still run through `onNewIntent`. More lists its entries as rows under a header with the member's name and role (from `/api/me`'s `display_name`; a sitter's header says whose plants they look after, from `owner_name`). Log out asks first, and offline says logging in again needs a connection. Logout calls the server and clears local credentials even if the network fails; that failure is not shown as an error. The login screen keeps one reserved line under Log in for progress and errors and names the server's reason for a refused login (`not_member`, `access_denied`, `server_error`). Session loss also clears the member-scoped Room and thumbnail caches and cancels background refresh.

At startup, and again after login, `/api/meta` gates on 426 or a newer semantic `minAppVersion`. The update stop names this version and the server's minimum, offers "Get the update" (the repository's latest release), "Open Obtainium" when it is installed, Check again and Log out. A missing endpoint, 404, remains compatible with older servers. The real meta response also carries serverVersion, today, timezone and role; a null minAppVersion imposes no minimum. The request sends `X-App-Version`. Network failures show a retry message instead of an update requirement.

More → About shows the app and server versions, the data sources with links and the source code link, and copies at most 64 predefined error events, bounded to 8 KiB. Exceptions, intent URLs, response bodies and user input cannot enter that log. The crash handler records only APP_CRASH and terminates without logging throwable text. No tokens, authorization codes or verifiers enter diagnostics.

Nothing queues writes in Room or WorkManager.

Opening the app, returning to it, login and pull-to-refresh refresh both task views and the plant list. Network loss, DNS failure and connect/read timeouts mark data offline. Server failures and malformed responses instead show `Fytorium isn't responding`. Both states keep cached data and disable writes until a successful refresh. A connected transport alone cannot clear either state. WorkManager reads every six hours, with a six-hour initial delay, a connected-network constraint and a battery-not-low constraint. Logout/session loss cancels its unique job.

Thumbnails use a custom disk cache rather than another image dependency. Only `/api/photos/:id/thumb` is fetched, with a 1 MiB per-thumbnail read bound and a 50 MiB total cap. SHA-256 filenames avoid storing URLs. Reads update LRU timestamps; writes evict oldest entries until under the cap. Full-size photos, tokens and login codes never enter either domain cache. Bitmap decoding uses Android's built-in API. Cache, repository, logout failure, member-switch failure, in-flight logout, offline writes and eviction tests exercise their public interfaces against Room, disk and MockWebServer. WorkManager tests inspect its public WorkInfo constraints, period and cancellation.

## Android releases

Only tag pushes matching `android-vX.Y.Z` on `SpyrosPsarras/epaflix-fytorium` can run the release job. Pull requests and forks cannot sign or publish. Actions are SHA-pinned. Only that job has `contents: write`; checkout does not persist the token.

The tag supplies `versionName = X.Y.Z` and `versionCode = X*10000 + Y*100 + Z`. Components have no leading zeroes, Y and Z are at most 99, and versionCode must be 1 through 2100000000. CI queries all published Android releases, including prereleases, and refuses a code equal to or lower than any published code. Drafts do not count. Missing permissions or a failed query stop the job.

Before signing, CI runs `build`, `test`, `lint`, `screenshots` and `release-check` through `./scripts/android`. It then builds the R8-minified APK with the production key, verifies the APK's version and signing certificate with SDK tools, and writes `SHA256SUMS`. The GitHub Release contains `fytorium-X.Y.Z.apk`, `SHA256SUMS`, the version, the certificate fingerprint and an `android/`-only git changelog since the previous published Android tag. The first release includes all Android history.

Gradle reads `ANDROID_RELEASE_TAG` for the version. Release signing uses `ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD` and `ANDROID_KEY_ALIAS`. The PKCS12 store and key passwords are the same. Without a keystore path, `release-check` still builds an unsigned APK. Debug builds never use the release signing configuration.

Keep the permanent key backed up in Vaultwarden at `/Fytorium/fytorium - android signing`. GitHub Actions uses `ANDROID_KEYSTORE_B64`, `ANDROID_KEYSTORE_PASSWORD` and `ANDROID_KEY_ALIAS`. Never regenerate this key for an update, commit it, or put it in a build artifact. CI decodes it with mode 0600 into `$RUNNER_TEMP`, mounts that file read-only for signing, and deletes it even when building or verification fails. No Firebase secret is required by this release pipeline yet; A12 supplies optional Firebase configuration later.

The production signing certificate SHA-256 is:

```text
8A:A9:74:16:85:B7:03:12:75:7F:44:37:2E:B0:36:3B:16:F2:C6:A9:11:03:6C:EE:77:7A:9F:39:11:62:0C:F7
```

### Local dry run

```sh
./scripts/android release-dry-run android-v0.1.0
# Exercise the same monotonic-version gate without GitHub or credentials:
PUBLISHED_TAGS='android-v0.1.0' ./scripts/android release-dry-run android-v0.1.1
```

The Docker-only dry run validates the tag, generates a one-day throwaway PKCS12 key inside its container, builds the signed release APK, checks its version and certificate with `apksigner verify --print-certs`, and prints the checksum. It also confirms that the production fingerprint check rejects the throwaway key. The key is deleted on exit. Its APK and `SHA256SUMS` stay in the ignored `android/app/build/outputs/fytorium-releases/<tag>/` directory. Never publish or install it over a production build. Without `PUBLISHED_TAGS`, local validation has no published-release history; CI always queries GitHub. `./scripts/android test` also exercises tag bounds and non-increasing versions.

## Bump the minimum app version
